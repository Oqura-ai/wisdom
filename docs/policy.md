# Data-layer policy

Wisdom's value is evidence an agent can trust, read at the smallest context cost.
Storing evidence is easy; reading it without bloating a context window, and without
losing reliability, is the product. These rules govern every change to how evidence is
recorded, stored and read, and every integration with a harness or another service.
Their aim is that any mistake can be seen and undone by a person, without losing evidence.

## 1. Evidence rules

These hold for every change. A change that breaks one is wrong, however useful.

1. **Record, never rewrite.** Records are append-only. Payloads are stored by SHA-256.
   Native transcripts are copied byte for byte. Nothing is edited or deleted in place; a
   correction is a new record that points to the old one.
2. **One copy of each body.** A body is stored once and referenced. Views point to
   evidence; they do not copy it into new stored forms.
3. **No model in the evidence path.** Nothing generated by a model is stored or returned
   as evidence. A future derived feature (a summary, a score) is stored apart from
   records, labelled as derived, and can be deleted without touching evidence.
4. **No silent loss.** What was not recorded is marked where it would have been:
   `not recorded` gaps, `redacted` thinking, `external-or-unknown` changes,
   `no result recorded`, `unreadable` bodies.
5. **Honest labels.** Timing is not authorship (`observed during c1`). A finished tool is
   not correct code. A recorded explanation is not hidden reasoning.

## 2. Reading rules (the ledger)

The ledger ([src/discovery.ts](../src/discovery.ts)) is how agents read. It follows how a
person explores a session: look at the shape, skim the headlines, open the odd one, read
the smallest proof, check the claim, stop.

1. **Two moves.** `glance` and `open`, addressed by position (`t3`, `t3/c2`, `a1`,
   `outside`). Positions are the address; agents never copy record IDs. A new move or
   parameter is added only when all of these hold:
   - an agent question the current moves cannot answer is written down;
   - its effect is measured on recorded sessions with known answers (correct answers,
     tokens read, confident wrong answers);
   - the code, tests, [vocabulary](vocabulary.md), the
     [skill](../skills/wisdom-ledger/SKILL.md) and the docs change together.
2. **No content rule cuts tool output or patches.** The only limit is the declared
   ceiling (80,000 characters per response), and it cuts at a line boundary. Any rule that
   would choose which lines of an output or patch matter belongs to a later, explicit,
   per-client version, never the default.
3. **Every limit says how to continue.** A limited response ends with the exact request
   for the rest, pinned to the same version.
4. **Show each piece of evidence once.** De-duplication points to where the evidence is
   shown (an edit's input is its patch; a file read is listed by size). It is declared per
   harness and per tool (`toolView`). Unknown tools, failed calls, and calls whose change
   was not recorded are shown in full. Opening a single call always shows it in full.
5. **Deterministic.** The same request at the same version returns the same text. Tests
   assert exact lines, so a change to the text is a visible diff in review.
6. **No envelope tax.** Metadata appears only where it changes the meaning (a gap, a
   pending result, an external change), never on every line.
7. **Plain words, not symbols.** Agents read text; `1 failed` beats a badge.

## 3. Integrations

### A new harness

Every harness is an adapter; none is central.

- **Its own directory.** Code in `src/harnesses/<name>/`, hook files in
  `integrations/<name>/`. The core reaches it only through
  [harnesses/index.ts](../src/harnesses/index.ts).
- **The full contract.** It implements every method of
  [HarnessAdapter](../src/harnesses/types.ts): `toolTarget`, `isDirectFileTool`,
  `toolView`, `nativeEntry`, `nativeSession`, `nativeCwd`, `nativePrompt`, `sessionFiles`.
  Unknown native entries must not throw; unknown tools are `full`.
- **Its home is the fence.** The harness keeps all its files in
  `.wisdom/harnesses/<name>/home/`, and `wisdom init` writes Wisdom's hooks into that
  home's own settings, so every process using the home records, however it was started.
  Wisdom never edits a user's global configuration; a harness outside the home is
  exactly as it was. Wisdom watches; it does not control how the harness runs its
  sessions (forks, branches, worktrees are the harness's own).
- **Or the project's own settings, with the person's own login.** `wisdom connect` adds
  Wisdom's hook to the harness's project-level settings, only where the harness documents
  loading them, and keeps them out of git (`.git/info/exclude`). It adds only its own
  entries, never edits a file git tracks, and `wisdom disconnect` takes out exactly what it
  added. Logins are never copied: a harness's refresh tokens can be single-use, so a copy
  would log the person out of their own tool. A project's copy of the hook stands aside in
  a tracked session, so no session is recorded twice.
- **Never blocks, never loses.** A hook never stops the harness. An event the daemon
  cannot take is kept in the spool and recorded later, marked late; the hook warns.
  A session whose hooks never ran is read from its own file and marked as such. Verify
  the harness's real hook behaviour with its installed version (Codex needs JSON output
  from every hook).
- **States its coverage.** What it records, what it cannot (the fog), and the harness
  version it was verified against, in its section of [harnesses](harnesses.md).
- **Tests.** Hook payload fixtures taken from the real version, a capture test that
  asserts the ledger's glance and open text, and an installed-binary check where possible.

### Another service (export, sync, sharing, review tools)

- **Reads only.** It reads through the ledger (`/ledger`) or the dashboard views
  (`/view`). It never writes to `records`, payloads or native copies.
- **Its own outputs, marked as derived.** Anything it produces lives in its own
  directory or table, is labelled as derived, and can be deleted without affecting evidence.
- **Opt-in, per invocation or per project.** A flag or a project file; no hidden global
  state, no background change to other tools.
- **Local and explicit.** Recordings are unredacted. Nothing leaves the machine unless a
  person runs a command that says so.

## 4. Keeping changes reversible

- **Storage changes are additive.** New tables, columns or record types only. Derived
  tables must be rebuildable from `records`, so they can be dropped and rebuilt.
- **Contracts are versioned.** A change to the daemon's contract bumps `CAPTURE_API`; a
  daemon from an older build is refused with a message that says how to restart it.
- **One change, one commit.** Code, tests and docs land together, so `git revert` plus a
  daemon restart undoes it. No migration rewrites evidence.
- **Destructive data operations need a person.** Deleting captures or a data directory
  is never automatic. Back up the whole data directory with the daemon stopped.
- **Rules name themselves.** Every rule that shows or omits something says so in the
  output (`input and output repeat p1`, `file content, N characters`, `limited`), so a
  reader can see why and get the rest.

## 5. Checklist for a change

- [ ] The evidence rules in section 1 still hold.
- [ ] No output drops, cuts by content, or rewords recorded evidence.
- [ ] Every omission names how to get what was omitted.
- [ ] The same request at the same version returns the same text.
- [ ] Tests assert the exact text that changed.
- [ ] The vocabulary, the skill and the docs describe the change.
- [ ] If it changes what agents read, its effect on correct answers and tokens was measured.
- [ ] A person can undo it with `git revert` and a daemon restart, with no evidence lost.

## 6. Known limits (v0)

- The ledger reads one session at a time. There is no search; reverse search from code
  to the turn that produced it is planned for multi-agent work.
- What a harness does not report cannot be read (encrypted thinking, tool paths that
  bypass hooks, other processes' edits). Harnesses built with partners can close more of
  this gap.
- A subagent that fails or is cut off before its stop event has no transcript copy, token
  usage or report, and no gap marks this yet; this breaks rule 1.4 and is the next fix. No
  success or failure is recorded for a subagent as a whole.
- The ceiling is measured in characters, not tokens; code and JSON can use more tokens
  per character than prose.
