# Pi to Wisdom: three-day learning and build sprint

Research checked: 2026-10-13.

## Outcome

In three intensive days, build one narrow but complete path:

```text
Pi process
  -> lossless raw capture
  -> normalized causal ledger in SQLite
  -> query API
  -> small post-session dashboard
```

The result is not the final Wisdom architecture. It is a learning implementation that proves the central idea using one runtime.

By the end, you should be able to explain and demonstrate:

1. The difference between Pi's live event stream and its persisted session tree.
2. The difference between timestamp order, protocol correlation, session lineage, and causality.
3. Why raw records remain authoritative even after normalization.
4. How an idempotent importer turns provider-specific records into a shared schema.
5. How an API can disclose context progressively without loading a complete transcript.

## Important Pi distinction

Pi exposes two useful but different views:

- `--mode rpc` and `--mode json` emit live execution events such as agent, turn, message, tool, retry, and compaction events.
- Pi's session JSONL stores durable session entries. Those entries form a branchable tree through `id` and `parentId` and are used to reconstruct model-visible context.

The session tree already preserves conversation lineage, but it is not the complete execution ledger. The live stream contains transient execution detail; the session file contains durable context entries. Wisdom must preserve both and link them where the source provides a reliable identifier.

Do not flatten these records into a transcript and call that causality.

## Scope

### Build during this sprint

- A TypeScript subprocess host for `pi --mode rpc`.
- A strict LF-delimited JSONL decoder.
- An append-only raw journal covering stdin commands, stdout records, stderr, process lifecycle, and session-file imports.
- A small normalized schema for runs, events, causal edges, artifacts, and coverage gaps.
- Idempotent normalization into SQLite.
- Read-only HTTP endpoints.
- A minimal session timeline and event-detail page.
- Fixtures and tests for malformed records, chunk boundaries, duplicate imports, branches, and missing links.

### Explicitly defer

- Claude Code and Codex adapters.
- Fleet orchestration.
- Production OpenRig integration.
- Semantic search, embeddings, and vector databases.
- Automatic summaries.
- Cloud synchronization and multi-user authentication.
- Reconstructing hidden model reasoning.
- A polished React application.

The sprint fails if it produces a broad architecture with no working vertical slice.

## Working location

Keep the learning implementation isolated here:

```text
learn/pi/
  README.md
  DAY-1.md
  DAY-2.md
  DAY-3.md
  RESOURCES.md
  JOURNAL.md
  lab/                 # create during Day 1
    src/
    test/
    fixtures/
    data/              # ignored; contains local session content
```

Do not initially patch OpenRig's Pi runner. Its launch, resume, process observation, environment allowlist, and durable cursor behavior are high-risk integration paths. Study them as a reference, then integrate only after the standalone contract is tested.

## Technology constraints

Use the same basic stack as the OpenRig checkout so later integration is unsurprising:

- Node.js 22 or 24
- TypeScript with ESM
- Vitest
- `better-sqlite3`
- Hono for the local HTTP API
- Plain HTML/CSS/JavaScript for the first dashboard

Do not add a graph database. SQLite tables are sufficient for this experiment.

## Three-day map

| Day | Learn | Build | Exit artifact |
|---|---|---|---|
| 1 | Pi RPC, JSONL framing, subprocess I/O, backpressure, raw provenance | Pi capture harness and raw journal | A real Pi run can be replayed byte-for-byte at the record level after Pi exits |
| 2 | Event sourcing, causality, lineage, correlation, provenance, idempotency, SQLite transactions | Normalizer, relational schema, causal edges, coverage gaps | The same fixture can be imported twice without duplication and queried as a graph |
| 3 | Read models, HTTP resource design, progressive disclosure, dashboard projections | API, timeline, event inspector, handoff export | A browser and another program can inspect the same durable run without reading Pi files directly |

Open the detailed file for each day and complete it in order.

## Daily learning loop

Use this loop for every concept:

1. **Predict:** write what you currently believe in `JOURNAL.md`.
2. **Read/watch:** use the required sources, not summaries generated by an agent.
3. **Explain:** restate the idea in your own words without looking at the source.
4. **Experiment:** create the smallest program or SQL query that exposes the behavior.
5. **Implement:** add it to the lab only after the experiment works.
6. **Test:** encode the failure mode you just learned.
7. **Reflect:** record what changed in your mental model.

If you cannot explain why a field or table exists, do not add it.

## Evidence rules

For every normalized field, be able to answer:

- Which raw source record supplied it?
- Is it copied, derived, or inferred?
- Can it be reproduced deterministically?
- What happens when it is absent?
- Which version of the Pi contract was observed?

Use these confidence classes:

```text
observed   The source explicitly emitted the fact.
derived    A deterministic transformation of observed records.
inferred   A documented heuristic that may be wrong.
unknown    The relationship cannot be established.
```

For the three-day build, causal edges should normally be `observed` or `derived`. Prefer a coverage gap over a speculative `inferred` edge.

## Start-of-sprint inventory

Before reading deeply, record these in `JOURNAL.md`:

```powershell
node --version
npm --version
pi --version
pi --help
Get-Command pi | Format-List Source,Version
```

Also record:

- Pi package name and installed version.
- Location of its installed documentation and TypeScript declarations.
- Operating system and shell.
- Whether a model credential is available for one controlled test session.

The installed CLI and its bundled declarations are authoritative for the installed version. The online Pi documentation tracks current `main` and can be newer.

## Final demonstration

Use one disposable repository and ask Pi to:

1. Read a file.
2. Make a small change.
3. Run a command that intentionally fails.
4. Correct the change.
5. Run a passing verification command.

Then stop Pi and demonstrate:

- The raw journal still contains every captured protocol record.
- Stderr and process exit are visible but not confused with Pi session events.
- The session file was imported without modifying it.
- The normalized event timeline points back to raw source records.
- Tool calls and results are linked by stable identifiers when Pi supplied them.
- Branch/session parent links remain distinct from execution-causality edges.
- Missing relationships appear as coverage gaps.
- Reimporting the same source adds zero duplicate records.
- The API and dashboard can answer what happened, what changed, what failed, and what verified the result.

## Definition of done

The sprint is complete only when all of these are true:

- [ ] One real Pi run is captured.
- [ ] Arbitrarily split stdout chunks are decoded correctly.
- [ ] `U+2028` and `U+2029` inside JSON strings do not split records.
- [ ] Malformed stdout and all stderr are preserved.
- [ ] Each source record has provenance, capture sequence, and integrity hash.
- [ ] Raw data is never rewritten by normalization.
- [ ] The database enforces idempotent source ingestion.
- [ ] The ledger distinguishes ordering, correlation, lineage, and causal edges.
- [ ] Unknown relationships are explicit gaps.
- [ ] API responses are read-only projections over stored records.
- [ ] The dashboard does not become a second source of truth.
- [ ] Tests pass from a clean checkout using fixtures without spending model credits.
- [ ] `JOURNAL.md` contains your explanations and final design decisions.

## Recommended intensity

Plan for 10 focused hours per day plus breaks. If a section takes longer, reduce UI polish before reducing capture correctness, provenance, or tests.

The priority order is:

```text
raw truth > identifiers > idempotency > causal links > queries > presentation
```
